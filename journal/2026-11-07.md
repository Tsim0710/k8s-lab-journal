Ушли от общего admin.conf: свой пользователь по сертификату, права группе через GitOps,
ServiceAccount для программы с минимумом прав.

## Пользователь — это не объект

В Kubernetes нет объектов «пользователь» и «группа». Имя и группы приходят с каждым запросом
вместе с учётными данными: у клиентского сертификата CN — имя, O — группы. Хранится только RBAC.

Выпуск через CSR API: ключ генерируется у себя и никуда не уходит, в кластер едет только запрос.
Подписант `kubernetes.io/kube-apiserver-client`, срок 30 дней. После создания запрос висит в
`Pending`, пока его не одобрят, и вот здесь главное: подписант подписывает любой subject, включая
`O=system:masters`. Проверять содержимое должен тот, кто одобряет, больше некому.

Первый вход с новым kubeconfig:

```
Username   ivan
Groups     [lab-devs system:authenticated]
Error from server (Forbidden): pods is forbidden: User "ivan" cannot list resource "pods" ...
```

Аутентификация прошла, авторизации нет — так и должно быть у пользователя без привязок.

## Права — группе и через git

Привязки лежат в gitops, приложение ArgoCD `rbac`: группе `view` на весь кластер и `edit`
RoleBinding'ом в трёх namespace приложений. Встроенная ClusterRole `edit` описана один раз,
RoleBinding ограничивает её своим namespace. В платформенные namespace `edit` не дан: он
позволяет запустить под с любым ServiceAccount и получить его права.

После пуша приложение не появилось несколько минут: вебхука из GitHub нет, ArgoCD опрашивает
репо раз в три минуты. Ускоряется аннотацией `argocd.argoproj.io/refresh=normal`.

Проверка `auth can-i` от имени нового пользователя совпала с ожиданием: поды и секреты в своих
namespace — да, поды в `monitoring` — да, секреты и удаление там — нет, ноды и
clusterrolebindings — нет.

## Ловушка с `--as`

```
$ kubectl auth can-i list pods -n otel-demo --as ivan
no
$ kubectl auth can-i list pods -n otel-demo --as ivan --as-group lab-devs
yes
```

`--as` подменяет только имя. Групп кластеру взять неоткуда, запрос идёт с одной
`system:authenticated`, а права выданы на группу. Проверяя чужие права, надо знать его группы.

## ServiceAccount с минимумом

Свой SA и своя Role: только `get/list/watch` на поды в одном namespace, не встроенная `view`.
Проверка из пода curl'ом с токеном из `/var/run/secrets/kubernetes.io/serviceaccount`:

```
demo/pods        200
demo/secrets     403
otel-demo/pods   403
```

Первый запуск через `kubectl run -i --rm` вывод потерял: команда закончилась раньше, чем
kubectl подключился к контейнеру, а `--rm` удалил под с логами. Надёжно — `run`, `wait` до
`Succeeded`, `logs`, `delete`.

## Чего не делали

- В основной kubeconfig пользователя не переносили — на каждый день по-прежнему admin
- OIDC: для людей в проде правильный путь, потому что сертификат не отзывается — права снять
  можно, а аутентификация живёт до конца срока. Схема записана, руками не поднимали
- Аудит apiserver не включали
