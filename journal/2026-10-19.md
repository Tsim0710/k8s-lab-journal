## etcd изнутри

Конспект писался по документации, живой кластер поправил его в трёх местах.

**«etcd слушает только localhost» — неправда.** На localhost смотрит apiserver,
а сам etcd по умолчанию kubeadm вешает ещё и на адрес ноды. Базу защищает mTLS:

```
curl https://127.0.0.1:2379/version                 → certificate required
curl --cert <сертификат от чужого CA> ...           → unknown ca
curl --cert etcd/healthcheck-client.crt ...         → {"etcdserver":"3.6.8",...}
```

Собственной авторизации в etcd нет (`auth status: false`) — любой сертификат от
etcd CA означает полный доступ к базе.

**`kubectl exec` в etcd идёт через apiserver.** Когда apiserver лежит, этот путь
мёртв, а `crictl` на нодах не установлен. Обход — `ctr tasks exec` прямо
в контейнер; упаковал в `make etcd`.

**«Всё лежит в protobuf» — только встроенные типы.** Pod начинается с `k8s\0`
и бинарного тела, а Application ArgoCD (CRD) — обычный JSON.

Самое интересное — MVCC на временном ConfigMap:

| Шаг | create_revision | mod_revision | version | resourceVersion |
|---|---|---|---|---|
| create | 79586 | 79586 | 1 | 79586 |
| patch | 79586 | 79589 | 2 | 79589 |
| тот же patch | 79586 | 79589 | 2 | 79589, `no change` |

`resourceVersion` в Kubernetes — буквально `mod_revision` из etcd. Счётчик общий
на весь кластер: за три секунды между create и patch его подвинули lease нод
и events. Удалённый ключ ещё читается по старой ревизии, пока apiserver не сделает
компакцию (раз в 5 минут), а после неё и watch, и `get --rev` получают
`required revision has been compacted` — в API это 410 Gone, после которого
информеры перечитывают список целиком.

## Шифрование секретов в etcd

До: значение секрета в etcd начинается с `k8s\0`, пароль Postgres находится
`grep`'ом. После: `k8s:enc:secretbox:v1:key2:` и шифротекст.

Решения, коротко:

- **secretbox**, а не aescbc (padding oracle) и не aesgcm (обязательная смена
  ключа каждые ~200 тысяч записей). Для прода правильнее KMS v2 — тогда главного
  ключа нет на диске ноды
- **Флаги через `kubeadm-config`, а не `sed` по манифесту.** `kubeadm upgrade`
  пересобирает манифесты из этого конфига. Шифрование, включённое `sed`'ом,
  пропало бы на апгрейде — и все секреты стали бы нечитаемыми. Заодно туда же
  записал открытые метрики control-plane: их когда-то открывали `sed`'ом
- **Автоперезагрузка конфига** — ротация ключа без рестарта apiserver
  (перечитал за 26–32 секунды)
- **Ротация сразу.** Процедура нужна в плохой день, учиться ей тогда поздно

Неожиданное — что остаётся на диске после включения:

| Момент | Старая версия через etcd | файл `db` | WAL от 28.09 |
|---|---|---|---|
| сразу после перешифровки | читается | есть | есть |
| после компакции | `compacted` | **есть** | есть |
| после `defrag` | — | **нет** | есть |

После компакции etcd старую версию уже не отдаёт, но байты лежат в освобождённой
странице bbolt — стирает только `defrag`. А в журнале WAL пароль останется, пока
etcd не вытеснит старый сегмент.

## Инцидент: сломал ArgoCD перешифровкой

Чтобы перешифровать старые секреты, сделал `kubectl replace` всех секретов. Для
Kubernetes это пустая запись, для ArgoCD — «объект изменился». `selfHeal` за две
секунды вернул `argocd-secret` к виду из Helm-чарта, а в чарте он пустой:
ключ подписи сессий и хеш пароля admin дописывает сам argocd-server при старте.
Итог — `server.secretkey is missing` вместо интерфейса.

Лечение: рестарт argocd-server (сам создал новый ключ) и возврат прежнего пароля.
Подвох — при рестарте сервер выдал admin новый случайный пароль и перезаписал им
`argocd-initial-admin-secret`, так что старого пароля там уже не было; вернул из
своего хранилища доступов.

Защита — `ignoreDifferences` на `/data` этого секрета плюс
`RespectIgnoreDifferences=true`. Проверил, повторив тот же `replace`: ArgoCD снова
синкнул, данные на месте.

**Вывод:** перед массовой операцией в GitOps-кластере проверить, какие из
затронутых объектов принадлежат ArgoCD и у кого содержимое пишется в рантайме,
а не берётся из git.
