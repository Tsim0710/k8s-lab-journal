Был один мастер, и его адрес `10.0.1.100:6443` стоял во всех kubeconfig. Стало три мастера,
etcd из трёх членов, а точка входа — VIP `10.0.1.10:8443`, который переезжает между ними.

## Схема

На каждом мастере HAProxy на порту 8443 отдаёт запросы любому живому apiserver, а живость
проверяет по `/readyz`. Порт 8443, потому что 6443 занят своим apiserver. keepalived решает,
кто из мастеров держит VIP.

В GCP два препятствия. Multicast нет, поэтому VRRP идёт unicast, и пакеты протокола 112 между
машинами доходят, это видно в `tcpdump`. Второе — сеть не верит ARP: пакеты на адрес получает та
машина, к которой адрес привязан в API. Поэтому новый главный мастер сам снимает alias IP с
прежнего хозяина и вешает на себя. API заодно служит арбитром: у alias не бывает двух хозяев,
и раздвоения VIP не будет даже при разрыве связи между мастерами.

Права на это — у отдельного сервисного аккаунта со своей ролью из пяти прав, без права удалять
машины.

## Перевод на VIP

Старый адрес нашёлся в семи местах. Перевёл шесть: `controlPlaneEndpoint`, `admin.conf`, kubelet
воркеров, kube-proxy, `cluster-info`, Cilium. kubelet, controller-manager и scheduler на мастерах
оставил на своём apiserver, через VIP им ходить незачем.

Первым шёл сертификат apiserver с VIP в SAN. Иначе любой клиент, пришедший на VIP раньше, упал бы
на проверке имени. CA тот же, поэтому новому сертификату доверяют сразу, а apiserver перечитал его
с диска за 5 секунд, без рестарта.

## Join мастеров

Перед join на новую ноду копируется ключ шифрования секретов: без него apiserver не стартует.
Проверка после — apiserver нового мастера расшифровал 54 секрета.

Между вторым и третьим мастером кластер был самым хрупким за всё время. У etcd из двух членов
кворум 2 из 2: падение любого остановило бы запись. Поэтому третий — сразу за вторым, а снимок
etcd — до обоих. etcd kubeadm добавляет learner'ом, членом без голоса, пока тот не догонит данные.

## Отказы

Простой — глазами клиента на воркере: `/readyz` через VIP пять раз в секунду.

| Отказ | Простой |
|---|---|
| остановлен keepalived на главном мастере | 21.4 с |
| `reset` главного мастера, после переделки скрипта | 8.9 с |

В первом замере сами операции GCP заняли 6.4 секунды, а 15 съел `gcloud`: каждый запуск — Python
из snap и новый токен. Скрипт переписан на `curl` в REST API с токеном из metadata-сервера,
холостой прогон — 1.4 секунды. Во втором замере около 3 секунд ушло на обнаружение и около 6 на
две операции GCP подряд. Быстрее с alias IP не получится.

Второй замер показал дыру опаснее простоя. Проверка keepalived ходит через свой HAProxy, а тот
по кругу отдаёт запросы и мёртвому apiserver, пока не исключит его. С `timeout connect 5s` против
2 секунд у проверки она зависала на обоих живых мастерах. Ещё один провал подряд на обоих — и VIP
не достался бы никому. Теперь HAProxy ждёт соединения секунду и уходит на другой apiserver.

## Что сломалось по дороге

- `node-prep` упал на третьей ноде: на свежей машине пакетный менеджер был занят
  `unattended-upgrades`. Скрипты теперь ждут блокировку
- apt без версии поставил бы kubeadm 1.36.6 при кластере 1.36.5: версии закреплены
- `keepalived -t` падает с кодом 5 на предупреждении о VIP. Пришлось указать `virtual_ipaddress`
- Рестарт keepalived на главном мастере сам вызывает переезд VIP. Скрипт установки теперь
  трогает только изменившиеся конфиги и делает `reload`

## Где это перестанет работать

Внешний адрес API остался только у первого мастера: упал он — с ноутбука нужен туннель на другой.
Все три мастера в одной зоне. Переезд VIP зависит от API GCP: если тот лежит, VIP не переедет.
