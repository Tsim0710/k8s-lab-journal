## Простыми словами

`kubectl` с ноутбука ходит в API кластера по внешнему адресу мастера. По пути: наш сетевой доступ
(VPN), firewall в GCP, сам API-сервер. «Не подключается» почти всегда значит, что сломался путь, а
не кластер.

## Как разбирать

1. **Что именно:** таймаут — пакеты не доходят (сеть, firewall, машина выключена); `connection
   refused` — машина жива, API не слушает; `x509` — сертификат или часы; `Unauthorized` — kubeconfig
2. **Машина работает:** `make lab-status`
3. **Путь через VPN:** `make my-ip` — показывает текущий адрес, что записано в tfvars и что реально
   стоит в firewall. Белый IP сменился и туннель не держит маршрут к API — закрыто
4. **Обход сети:** `make api-tunnel` — API через IAP на localhost, без firewall и VPN
5. **На мастере** (`make ssh-cp`): `sudo crictl ps | grep kube-apiserver`, логи apiserver и etcd

## Как чинить

- VPN не поднят или маршрута к API нет — поднять, адрес API в списке маршрутов туннеля
- Адрес в firewall не тот — правка `my_ip_cidr` в tfvars **вместе** с переменной CI `MY_IP_CIDR`,
  иначе CI откатит firewall обратно
- apiserver не стартует — смотреть логи; часто это etcd или сертификаты

## Чтобы не повторилось

Проверка доступа должна смотреть на реальное правило firewall, а не на конфиг: так `make my-ip`
однажды говорил «всё совпадает», а API был закрыт.

## Было у нас

19.10: `make my-ip` сравнивал адрес с tfvars, а не с firewall. 02.11: белый IP сменился в очередной
раз — API перевели на WireGuard, смена IP больше ни на что не влияет.
